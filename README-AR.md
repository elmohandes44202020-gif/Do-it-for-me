# سيرفر NotebookLM → MP3 → رابط تحميل مباشر

خدمة صغيرة (FastAPI) تُنشر على **Faable Deploy** بالخطة المجانية. تستقبل روابط الحلقات الصوتية من دفتر NotebookLM، تنزّلها **على السيرفر**، تحوّلها من `m4a` إلى `mp3` بمكتبة **PyAV** (بدون ffmpeg)، ثم تعطيك رابطًا لملف ZIP.

مُختبَرة محليًا من أولها لآخرها: تنزيل ← تحويل ← أرشيف ← تحميل (`python test_e2e.py`).

---

## 1) لماذا هذا التصميم يناسب الخطة المجانية

| القيد على Faable Free | كيف تعاملنا معه |
|---|---|
| `bi.xs` = 0.6 vCPU · **512 MB** | تحويل **بثّي** إطارًا بإطار: ذروة الذاكرة ≈ 40 MB مهما طال الملف. مهمة واحدة في نفس الوقت (طابور داخلي). |
| Docker ممنوع · Python buildpack فقط | `main.py` + `requirements.txt` + `runtime.txt` — لا `apt`، لا ffmpeg، لا Dockerfile. |
| **لا قرص دائم** | كل شيء في `/tmp/nlm/<job>`، ويُحذف تلقائيًا بعد `TTL_MINUTES`. |
| النوم بعد 30 دقيقة خمول | المهمة تُنفَّذ داخل الطلب الحالي (Thread)، والنتيجة تُحمّل قبل انتهاء الـTTL. |
| 10 GB/شهر · 1 GB/يوم تحميل | الـZIP يُرسل **بثًّا** بلا نسخة إضافية على القرص. وبتقليل البِتريت يقلّ الحجم فعليًا. |
| لا Workers / Always-on | لا نحتاجهما: طابور في الذاكرة + Thread واحد. |

**أرقام مقيسة فعليًا:** ملف `m4a` مدته 5 دقائق (AAC 128k ستيريو = 4.85 MB) صار `mp3` 96k **مونو** = 3.60 MB — أي **−26%** في الحجم، وفي 2.1 ثانية بذروة ذاكرة 38 MB. لو ضبطت `MP3_BITRATE=64000` يصبح التوفير ≈ **−50%** (كلام بشريين لا يحتاج أكثر).

## 2) النشر على Faable (خمس دقائق)

1. أنشئ مستودعًا على GitHub وضع فيه هذه الملفات في الجذر:
   ```
   main.py  media.py  zipstream.py  requirements.txt  runtime.txt  faable.json
   ```
   > `runtime.txt` مهم: يثبّت بايثون 3.12 لأن حزم `av` الجاهزة (wheels) متوفرة لها بشكل مؤكد. لو تركته سيعطي Faable 3.14 وقد يفشل بناء `av`.
2. من [لوحة Faable](https://dashboard.faable.com/): **New app → Connect repository → اختر المستودع**.
3. في **Environment variables** أضف:
   ```
   API_KEYS = ahmed:<مفتاح-طويل-عشوائي>,sara:<مفتاح-آخر>
   TTL_MINUTES = 45
   MP3_BITRATE = 96000
   MP3_MONO = 1
   ```
   توليد مفتاح: `python -c "import secrets;print(secrets.token_urlsafe(24))"`
   كل صاحب حساب يحصل على مفتاحه الخاص — وكل مهمة معزولة عن غيرها.
4. Deploy. التحقق:
   ```bash
   curl https://<app>.faable.link/healthz
   ```

> بالخطة المجانية التطبيق **ينام بعد 30 دقيقة** من آخر طلب؛ أول طلب بعد النوم يستغرق ثواني إضافية (cold start). هذا طبيعي.

## 3) واجهة الـAPI

كل الطلبات تحتاج `X-Api-Key: <المفتاح>`، ما عدا `/healthz`.

| الطلب | الوظيفة |
|---|---|
| `GET /healthz` | حالة الخدمة والإعدادات (بلا مفتاح) |
| `POST /probe` | **هل الرابط قابل للتنزيل من السيرفر؟** يجرّب أولًا بدون كوكيز ثم معها → يخبرك `cookie_needed` |
| `POST /jobs` | ينشئ مهمة، يعيد `job_id` (202) |
| `GET /jobs/{id}` | التقدّم لكل ملف + `zip_url` عند الانتهاء |
| `GET /jobs/{id}/zip` | تنزيل الأرشيف مباشرة (`Content-Length` مضبوط → شريط تقدّم دقيق) |
| `GET /jobs/{id}/files/{n}` | تنزيل حلقة واحدة |
| `DELETE /jobs/{id}` | حذف المهمة وملفاتها فورًا |

### مثال: إرسال مهمة

```bash
curl -X POST https://<app>.faable.link/jobs \
  -H "X-Api-Key: $KEY" -H "Content-Type: application/json" \
  -d '{
    "zip_name": "notebooklm-audio",
    "files": [
      {"title": "الحلقة الأولى: مقدمة", "url": "https://lh3.googleusercontent.com/..."},
      {"title": "Episode 02 - Deep Dive",  "url": "https://lh3.googleusercontent.com/..."}
    ]
  }'
# → {"job_id":"a1b2c3d4e5f6","state":"queued","files":2}
```

### مثال: متابعة الحالة

```bash
curl -s https://<app>.faable.link/jobs/a1b2c3d4e5f6 -H "X-Api-Key: $KEY"
```
```json

  "state": "done",
  "progress_percent": 100,
  "total_bytes_out": 7201732,
```

## 4) موضوع الكوكيز — الجواب المباشر على سؤالك

سؤالك كان: «ما نبعث للسيرفر غير روابط التحميل، وأنا أسجّل الدخول على جهازي بأمان؟»

هذا هو **التصميم المفضّل**، وهو الافتراضي هنا: حقل `url` وحده يكفي، وحقل `cookie` **اختياري تمامًا**.
لكن جوجل تُصدر روابط صوت من نوع «موقّع/مرتبط بالجلسة»، وقد ترفضها من IP آخر. لذلك نبني على **الاختبار لا على التخمين**:

```
1) من التطبيق: POST /probe {url}
2) لو رجع cookie_needed = false  → أرسل الروابط فقط. لا سرّ يخرج من جهازك أبدًا. ✅
3) لو رجع cookie_needed = true   → السيرفر يولّد نفس الرابط بدون كوكيز (403/401)،
   وساعتها فقط أرسل الكوكي مع المهمة، وهي:
      • تُستخدم في الذاكرة،
      • تُمحى فور انتهاء التنزيل (`f.cookie = None`)،
      • لا تُكتب في أي لوج،
      • ولا تُحفظ على أي قرص.
```

لو كانت الإجابة `true` دائمًا، عندك ثلاثة خيارات بالترتيب:
1. **حساب جوجل مخصّص** لهذا الغرض فقط (أفضل توازن).
2. **دفتر مُشارَك للعامة** إن كان ذلك يناسبك — غالبًا يجعل الروابط تعمل بدون كوكيز.
3. **بدون سيرفر**: استخدم PyAV أو GitHub Actions كما في ورقة النقاش.

> ⚠️ الكوكي = مفتاح حسابك بالكامل. لا تشارك المفتاح ولا الكوكي، ولا تنشر المستودع بمفاتيح.

## 7) ملاحظات أمنية وحدود

- **SSRF محمي:** التنزيل مسموح فقط من نطاقات جوجل (`googleusercontent/googlevideo/googleapis/gvt*/gstatic/google.com`) — نفس قائمة `AudioTransfer.java`.
- **عزل المستخدمين:** كل مهمة مرتبطة بهاش مفتاحها؛ لا أحد يرى مهمة غيره.
- **لا تخزين دائم:** لا قاعدة بيانات ولا قرص. المهام في الذاكرة، فإعادة النشر (deploy) تُلغيها — وهذا مقصود.
- **الحد المجاني للترافيك:** 1 GB/يوم. أرشيف بـ 10 حلقات ≈ 150 MB، فأنت داخل الحد بسهولة، لكن لا تُكرّر التنزيل عشرات المرات في نفس اليوم.
- **حدود جوجل وشروط الخدمة:** الاستخدام الشخصي لملفاتك هو الأصل؛ لا تنشر الخدمة للعامة ولا تعطِ مفاتيحك لأحد.

## المسار المضمون: `POST /convert` (رفع من الهاتف)

الهاتف ينزّل الملف بجلسته التي تعمل فعلًا، ثم يرفعه للسيرفر للتحويل.

```
POST /convert     (multipart/form-data)
  meta  = {"titles":["الحلقة 1","الحلقة 2"],"bitrate":64000,"mono":true,"zip_name":"بودكاست"}
  files[] = الحلقات بصيغة m4a
→ 202 {"job_id":"…","files":2,"bytes":9705104,"mode":"upload"}
GET  /jobs/{id}            الحالة والتقدّم
GET  /jobs/{id}/files/{n}  ملف mp3 منفرد (يدعم Range)
GET  /jobs/{id}/zip        ملف مضغوط لكل الحلقات
```

## الكوكيز لكل نطاق (إصلاح جوهري)

كوكيز جوجل مرتبطة بنطاقها: كوكي `.google.com` **لا** تُرسل إلى
`googleusercontent.com`، وإرسالها هناك يجعل جوجل تعيد صفحة دخول
(CookieMismatch). لذلك صار المحرّك:

- يتبع التحويلات (302) **يدويًا**، خطوة بخطوة.
- يختار لكل قفزة **أطول نطاق مطابق** من `cookie_map`.
- يعيد سلسلة القفزات في تقرير الفشل: `#1 host → 302 … cookies=1 → /rd/…`

```
POST /diagnose  {"url":"…","cookie_map":{"google.com":"…","googleusercontent.com":"…"}}
POST /jobs      {"files":[{"url":"…","cookie_map":{"google.com":"…"}}]}
```

الكوكي المسطّحة (`cookie`) تبقى مدعومة لكنها تُعامل كنطاق `google.com` فقط.

## ملف الروابط النصي: «انسخ الرابط وسلّمه للسيرفر» (0.6.0)

بدل أن يحمل الهاتف أي بايت من الصوت، يعطيه **نصًّا**: الرابط النهائي بعد التحويلات.
السيرفر يفهم النص في أي صيغة ويبدأ التنزيل والتحويل.

```
POST /resolve      {"url":"…"}            ← يتتبّع التحويلات ويرجّع final_url كاملًا
POST /links        {"text":"…"}           ← نص فيه روابط (أو عنوان | رابط)
POST /links/file   multipart: file=links.txt + meta={}
```

الصيغ المقبولة داخل الملف: رابط وحده، `عنوان | رابط`، `عنوان<TAB>رابط`،
`[عنوان](رابط)`، سطر JSON، أو مصفوفة JSON كاملة. الروابط المكررة تُحذف،
وغير المسموح يُرفض ويُدرج في `rejected` بدل إفشال المهمة.

> `POST /convert` (رفع الملفات) ما زال موجودًا كخطة احتياطية فقط.

## أسماء الملفات داخل الـZIP (0.6.0)

الاسم = **عنوان الحلقة في NotebookLM كما هو** + `.mp3`. لا ترقيم، لا بادئات، لا لاحقات.

- المحارف الممنوعة على أنظمة الملفات (`/ \ : * ? " < > |`) تُستبدل بمسافة فقط،
  لأن وجودها يمنع فكّ الضغط أصلًا على أندرويد/ويندوز.
- الأسماء الطويلة تُقصّ عند 120 حرفًا (حد نظام الملفات).
- لو تكرّر عنوانان بالحرف نفسه: الثاني يأخذ `(2)` والثالث `(3)` — لأن مجلدًا واحدًا
  لا يقبل ملفين بنفس الاسم.
- العنوان الفارغ (نادرًا) يصبح `حلقة N.mp3`.
- أسماء الـZIP بصيغة UTF-8 مع ضبط علم اللغة (bit 11) فتظهر عربية سليمة على كل الأنظمة.

## لوحة إدارة: `GET /jobs` (0.6.0)

يسرد كل مهام المستخدم وحالتها **بدون تحميل أي ملف** — يستخدمه التطبيق في
«🗂 لوحة السيرفر»:

```json
{"count":1,"queued":0,
 "limits":{"max_files":20,"max_job_mb":250,"ttl_minutes":45},
 "jobs":[{"job_id":"…","state":"done","name":"دفتر الملاحظات",
          "files_total":15,"files_done":15,"files_failed":0,
          "bytes_out":131072,"expires_in_sec":2400,
          "zip_url":"…/jobs/…/zip","failures":[]}]}
```

`failures` تحمل عنوان كل حلقة فشلت وسببها (حتى 300 حرف) — وبهذا يعرض التطبيق
«نجح X من Y» مع الأسباب بدل نجاح وهمي.

## 0.6.0 — مجموعات (دفتر ملاحظات كامل في ZIP واحد)

بدل الدفعات المنفصلة، التطبيق يرسل **كل** حلقات الدفتر في مجموعة واحدة:

| الطلب | الوظيفة |
|---|---|
| `POST /collections` | `{name, order_text, match, files:[{title,url,…}]}` → `collection_id` |
| `GET /collections` | كل المجموعات وحالتها (لوحة الإدارة) |
| `GET /collections/{id}` | تفصيل كل حلقة + السجل + الترتيب |
| `POST /collections/{id}/order` | إرسال/تعديل ملف الترتيب بعد البدء |
| `POST /collections/{id}/retry` | إعادة الحلقات الفاشلة وحدها |
| `POST /collections/{id}/finalize` | بدء الترتيب والضغط |
| `GET /collections/{id}/zip` | ملف ZIP واحد باسم دفتر الملاحظات |
| `DELETE /collections/{id}` | حذف المجموعة وملفاتها |

**الترتيب:** يُقرأ النص سطرًا سطرًا، ويُطابَق مع أسماء الحلقات بنسبة ≥ `match`
(50%–80%، الافتراضي 60%) بعد تطبيع (تجاهل الترقيم في أول السطر، التشكيل،
أ/ا، ى/ي، ة/ه، المسافات، `.mp3`). ثم **يُنقل** كل ملف بالترتيب إلى
`<اسم الدفتر>/تم الترتيب/` بفاصل `150ms` بين كل نقل، وبعدها يُبنى ZIP واحد.

كل حلقات الدفتر تبقى في مجلد واحد — لا مجلد لكل دفعة، لأن الترتيب يكون عالميًا.

متغيّرات البيئة الجديدة: `MAX_COLLECTION_MB` (1500) · `MAX_COLLECTION_FILES` (400) ·
`ORDER_MATCH` (0.60) · `ORDER_MOVE_DELAY` (0.15) · `COLLECTION_WORKERS` (2) ·
`SORTED_DIRNAME` (تم الترتيب).

## 0.9.2 — باقات كورسيرا (وضع المعالج في التطبيق 3.60)

نفس المحرّك المتوالٍ والرفع التلقائي، لكن الوحدة الأساسية «باقة دورة»: فيديوهات MP4
عربية مدمجة + ملفات ترجمة `*.ar.srt` + نصوص، تُسلَّم **ZIP** أو **مجلدًا** باسم الدورة،
ثم تُرفع إلى **MEGA** أو **Telegram**.

| المسار | الوظيفة |
|---|---|
| `POST /courses` | `{name, delivery:"zip"\|"folder", cloud:"mega"\|"telegram", auto, mega_session, tg_session}` → `{course_id,…}` |
| `POST /courses/{id}/files?name=…&kind=video\|srt\|txt\|other` | الجسم = بايتات الملف (بثّ) — 201، و409 بعد الإقفال |
| `POST /courses/{id}/finalize` | يبدأ الترقيم والتغليف (`packing` → `ready`) |
| `GET /courses/{id}` | الحالة + الملفات + `zip_url` + `mega`/`tg` |
| `GET /courses/{id}/zip` · `/file/{idx}` | تنزيل الباقة أو ملف مفرد |
| `POST /courses/{id}/cloud` | تغيير السحابة أو بدء الرفع بعد الجاهزية |
| `GET /courses` · `DELETE /courses/{id}` | القائمة والحذف |

**قاعدة الأسماء:** الترتيب هو ترتيب وصول الملفات (يرسلها التطبيق متوالية: فيديو ثم
ملفه `*.ar.srt`)، ويُعاد ترقيمها `001 - <الاسم>` مع تنظيف أي رقم قديم في البداية.
مجلد MEGA يُسمّى باسم الدورة، وباقات كورسيرا تُرفع في جذوره بلا مجلد «تم الترتيب».

اختبارات: `python3 t_course.py` (ZIP/مجلد + MEGA/Telegram) و`python3 t_wizard.py`
(عقد العميل نفسه الذي يستخدمه التطبيق).

## 0.9.6 — خانات تسجيل الدخول للسحابة + لوحتا عمليات

- **دخول MEGA من داخل خطوة الرفع**: بريد + كلمة مرور ⇒ تُشفّران على الهاتف (RSA-OAEP) ⇒
  `POST /mega/session` يفتح جلسة في الذاكرة فقط (لا تُخزَّن كلمة المرور على السيرفر ولا على الهاتف).
- **ربط بوت تيليجرام من نفس الخطوة**: توكن BotFather + معرّف المحادثة، و`POST /tg/detect`
  يكتشف معرّف محادثتك تلقائيًا من آخر رسالة وصلت للبوت.
- **`GET /cloud/status`**: التطبيق يسأل السيرفر «هل الجلسة شغالة؟» قبل ما يبدأ الرفع.
- **`GET /ops`**: لوحتا العمليات في التطبيق (تنزيلات + رفع) مع اسم مجلد الرفع داخل MEGA/تيليجرام.
- `POST /courses/{cid}/cloud` بقى صريحًا: 202 · 409 (غير مغلَّفة/لا ملفات) · 400 (لا جلسة) برسائل عربية.
- `mega_up.create_session`: في وضع `NW_FAKE_MEGA` يفتح جلسة بلا شبكة (للاختبار)،
  ولو حزمة `mega.py` ناقصة على السيرفر يعطي رسالة عربية واضحة: «ثبّتها بأمر pip install mega.py».
- اختبار: `python3 t_login.py` (خانات الدخول) و`python3 t_cloud.py` (الرفع + اللوحات).

## 0.9.4 — التنزيل على السيرفر (لا تنزيل على الهاتف)

بدل ما التطبيق ينزّل الفيديوهات على الهاتف ثم يرفعها، بقى الهاتف يبعت **روابط** المحاضرات
والترجمة للسيرفر، والسيرفر هو اللي ينزّل ويحوّل ويَدمج ويغلّف ويرفع.

| المسار | ماذا يفعل |
|---|---|
| `POST /courses` | يفتح باقة جديدة (state=`uploading`) — كما كان |
| `POST /courses/{cid}/fetch` | 202 — يبدأ التنزيل على السيرفر من قائمة عناصر `{name,kind,url,subtitle{url,format}}` + `cookie` + `user_agent` + `embed` |
| `GET /courses/{cid}` | `fetch:{state,done,total,percent,current,mux,muxed,errors[],errors_count}` + `files[]` بترتيب الوصول |
| `POST /courses/{cid}/delivery` | `{"delivery":"zip|folder"}` قبل التغليف فقط (409 بعدها) |
| `POST /courses/{cid}/finalize` | يغلّف (ZIP أو مجلد) ثم يرفع MEGA/Telegram كما كان |
| `POST /courses/{cid}/cloud` | يختار السحابة ويبدأ الرفع لو الباقة جاهزة |

- الترجمة: VTT ⇒ SRT عربي، والدمج داخل MP4 بخيار `mov_text` (**ffmpeg خارجي**؛ لا PyAV للترجمة).
  ffmpeg يُبحث في PATH ثم في حزمة `imageio-ffmpeg` — أضفناها إلى `requirements.txt`.
- كل محاضرة تُنتج ملفين: `الاسم.mp4` (مدموج) + `الاسم.ar.srt`، والترقيم النهائي `001 - الاسم` يحدث وقت التغليف.
- فشل ملف واحد لا يُسقط الباقة: يظهر في `fetch.errors` ويتكمل الباقي.
- حماية SSRF: `http` مرفوض افتراضيًا، والعناوين الخاصة/المحلية مرفوضة إلا مع `COURSE_FETCH_ALLOW_LOCAL=1`.
- سقف الحجم `COURSE_FETCH_MAX_MB` (افتراضي 4096)، والملفات المؤقتة تُمسح بعد الدمج.

اختبار سريع: `python3 t_fetch.py` ⇒ «كل اختبارات التنزيل على السيرفر نجحت ✅».

## 0.9.3 — تصحيح معرّف محادثة تيليجرام ورسائل عربية نظيفة

**المشكلة:** `Forbidden: the bot can't send messages to the bot` — كان السيرفر يقبل معرّف
البوت نفسه في خانة المحادثة (لأن `getChat` ينجح عليه)، فيظهر العطل متأخرًا أثناء الرفع
بنص Bot API خام مع اسم كلاس (`RuntimeError:`).

**ما تغيّر:**
- `POST /tg/detect` جديد: يشفّر الهاتف التوكن وحده ⇒ السيرفر يقرأ آخر رسالة وصلت للبوت
  (`getUpdates`) ويعيد معرّف محادثتك الحقيقي.
- الربط `POST /tg/session` يرفض/يصحّح معرّف البوت تلقائيًا ويعيد `chat` الحقيقي +
  `chat_fixed` + `note` بالعربية.
- عند الإرسال `_tg_run` يعالج الجلسات القديمة المعطوبة: يصحّحها ويكتب ملاحظة في سجل
  المجموعة بدل إفشال الرفع.
- كل أخطاء تيليجرام تُترجم إلى جمل عربية واحدة (`friendly_error`)، وأخطاء ميجا/الجلسات
  لم تعد تحمل اسم كلاس (`_user_error`).

اختبار: `python3 t_tg_chat.py`.
